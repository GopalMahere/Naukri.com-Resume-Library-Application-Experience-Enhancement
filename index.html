Executive Context & Proposal Introduction

Good morning. My name is Aditya Sharma, and this is an independent Product Management case study proposing an enhancement for Naukri.com titled 'One Profile, Multiple Resumes'.

Job seekers frequently apply across varied role categories (such as Product Management, Consulting, Operations, and Core Tech). Today, candidates often maintain different resume versions tailored to these roles, but switching or managing them during portal applications can introduce unnecessary friction.

This proposal explores giving candidates a dedicated Resume Library within their single profile, allowing them to choose or upload the appropriate resume at the moment of applying without overwriting existing files.

Problem Statement & Candidate Context

In our discovery discussions, we observed that candidates naturally tailor their resumes depending on the role. An applicant targeting both Product Management and Management Consulting cannot highlight the exact same project narrative for both.

Consequently, candidates maintain multiple resume files. Creating them on a laptop is straightforward—the friction arises when applying across job portals.

Important distinction: we present this as an observed candidate experience that warrants structured validation across Naukri's application types.

The Three Core Components

The solution architecture consists of three cohesive components:

  • Component 1: One Comprehensive Profile: We maintain a single structured master record for skills, education, and career experience. This protects Naukri's core search and matching infrastructure.
  • Component 2: Dedicated Resume Library: Rather than forcing multiple profile creations, we provide a clean, isolated document library where files have custom user-defined names.
  • Component 3: Application-Time Resume Selection: The candidate transparently picks which document to attach at the moment of apply.
  • Control Principle: The system preselects the candidate's designated default resume for convenience, while strictly requiring explicit review and confirmation before submission. If no default is designated, selection is required.

Edge Cases & Data Integrity Rules
Duplicate Filenames: Treat duplicate filenames as separate uploads. Never treat identical filenames as permission to overwrite.
Upload Failures: Show clear error message and retry option; withhold the save checkbox until successful upload.
Post-Apply Library Deletions: Deleting a library resume removes it from future apply flows, but preserves the previously submitted application record intact.
External Website Applications: For jobs redirecting to external company portals, clearly communicate that resume selection and storage behaviour depends on the third-party system.

Step-by-Step Workflow & Edge Cases

Notice the detailed handling of edge cases in this workflow:

  • Scenario 1 (One Saved Resume): If a candidate only maintains one resume, we preserve the existing quick-apply experience. We do not burden single-resume users with an unnecessary selector.
  • Scenario 2 (Multiple Resumes): If multiple resumes exist, the selector displays them clearly with their custom names and original filenames.
  • Upload & Save Gate: If the candidate uploads a new document, the save checkbox appears ONLY after the upload succeeds. If unchecked, it is application-only. If checked, they provide a custom name and it saves as an independent document.
  • Data Integrity: Deleting a resume from the library never erases that document from past submitted applications.

Experimentation & Measurement Framework

To establish whether the feature improves the candidate experience, we propose a controlled A/B experiment:

  • Primary Metric: Application Completion Rate (Completed Applications / Application Starts). This measures whether candidates are genuinely more likely to complete applications when resume-switching friction is reduced/mitigated.
  • Secondary Metrics: We observe adoption patterns—how many candidates use existing library resumes, how many upload on the fly, and what percentage choose to save newly uploaded files.
  • Guardrail Metrics: Accidental overwrite incidents must strictly remain zero. We monitor support ticket volumes, upload failures, and ensure privacy rules are completely respected.
  • Statistical Parameters: We do not invent arbitrary MDE thresholds. The analytics team will define the sample size, duration, and MDE based on Naukri's actual traffic and baseline conversion variance.

Prepared by: Aditya Sharma  •  Scope: User Research, Product Discovery, UX Design, PRD, and Interactive Prototype

Core Hypothesis & Problem Statement

Candidates who apply across multiple job categories often maintain different resume versions, but managing and switching between those documents during the application journey can create unnecessary friction. This deck proposes giving candidates a centralized, candidate-controlled resume library that allows them to select the right resume at the moment of application, without repeatedly replacing their primary resume or maintaining multiple profiles.
