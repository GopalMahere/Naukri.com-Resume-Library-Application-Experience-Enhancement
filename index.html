A Resume Library Built Around Candidate Choice

Three core pillars and five foundational design principles for candidate control

Pillar 1 👤
One Comprehensive Profile
Single source of truth. Master education, verified skills, employment history, and contact details remain unified. No duplicate accounts or fragmented job histories.
Pillar 2 📁
Dedicated Resume Library
Dedicated candidate workspace storing role-specific resumes (proposed MVP capacity assumption: up to 5 resumes, subject to validation). Each document receives a custom label (e.g. PM CV, Consulting CV).
Pillar 3 ⚡
Application-Time Selection
Select from stored resumes directly inside the job application modal. Candidates can also upload a fresh resume with optional conditional saving to the library.
Five Foundational Design Principles
1. Candidate Control
The system never silently auto-submits a document without explicit candidate confirmation.
2. Privacy by Default
Library resumes remain private. Only the specific resume attached to an application is shared.
3. Independent Files
Uploading, editing, or deleting one resume has zero destructive impact on any other stored resume.
4. No Silent Overwrite
Uploads default to application-only unless the candidate explicitly checks to save as a new file.
5. Transparent History
Application history preserves an exact document reference of what was submitted to each employer.

Slide 10 — Proposed Solution Pillars (Suggested Duration: ~60 seconds)

Speaker Script: "Our proposed feature, Resume Library, rests on three clear product pillars:

  • 1. One Comprehensive Profile: A single source of truth for the candidate's career data—education, skills, work history. No secondary accounts.
  • 2. Dedicated Resume Library: A clean management area with a proposed MVP capacity of up to 5 resumes (subject to technical and user testing validation), with custom names like 'Product Management CV' or 'Consulting CV'.
  • 3. Application-Time Selection: An interactive selector inside the apply modal, allowing candidates to pick an existing resume or upload a new one.

This is guided by five foundational principles: candidate control, privacy by default (unselected resumes are never exposed to recruiters), independent files, zero silent overwriting, and transparent application history tracking."

Slide 11 — Future Workflow & Logic (Suggested Duration: ~75 seconds)

Speaker Script: "This slide clearly shows two distinct application paths the candidate can follow:

  • Path A — Select a saved resume: The candidate opens the apply modal, sees their library of custom-named resumes, selects one, reviews their selection (file name, company, role confirmed), and submits. No upload. No save checkbox. Direct and frictionless.
  • Path B — Upload a new resume: The candidate chooses to upload a fresh document. The save checkbox is strictly hidden while the upload is in progress. Only after the upload reaches 100% success does the conditional save gate appear. If unchecked (default), the file is used for this application only and the library is unchanged. If checked, the candidate must supply a mandatory custom name, and the file is saved as a new independent entry — no existing resumes are overwritten.

Both paths end with an explicit review screen before submission. No silent auto-submission. Application history preserves a reference to the exact version submitted.

Default-resume preference (pre-highlighting a designated default) is kept in future scope, not an MVP requirement.

Functional Requirements Prioritization
Priority Feature Requirement Scope

MoSCoW framework ensures lean MVP delivery for pilot validation.
Core Acceptance Criteria (Given / When / Then)
AC1: Conditional Save Gate
Given an in-flow upload, When upload is in progress, Then save checkbox is hidden. Checkbox renders only upon 100% upload success.
AC2: Mandatory Naming Validation
Given candidate checks 'Save to Library', When custom name is blank or whitespace, Then submission is blocked with inline error.
AC3: Duplicate Filename Handling
Given candidate uploads file named Resume.pdf, When existing file has same name, Then system assigns unique internal document identifier without overwriting.
AC4: Historical Submission Integrity
Given candidate modifies or removes a resume post-apply, When reviewing past applications, Then submitted record retains reference to the document version sent.
Proposed specifications for engineering review to prevent data collisions and ensure candidate control.
Technical Requirements for Engineering Evaluation: Document storage requires secure object/blob storage with unique document identifiers to prevent collisions. Candidate metadata requires relational mapping between candidate profile ID, library resume entities, and application submission logs. Search indexing integration (e.g. recruiter Resdex discovery) and synchronisation behavior must be formally evaluated by Naukri engineering.
Data Retention, Privacy & Legal Review: Document retention and deletion policies require formal review by Naukri engineering and legal teams to establish statutory compliance, storage lifecycles, and candidate data erasure protocols. Employer document access must remain strictly restricted to the specific resume selected for that application.
